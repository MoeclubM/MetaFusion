# 媒体编目与用户前端：能力核查和改进建议

核查日期：2026-09-23。本文讨论元数据及其展示；文件字节、哈希、访问控制由独立存储服务负责。代码证据以本仓库当前实现为准，参考页只作为要表达的真实业务样本，不把参考站的分类法原样搬进本系统。

## 1. 参考页实际提出的需求

- [Bangumi 动画条目 633836](https://bgm.tv/subject/633836) 是《Re:ゼロから始める異世界生活 4th season 奪還編》的作品页。页面把概览、章节、角色、制作人员、关联分开；核查时章节列出 78–85，并给单集题名、首播日、时长。角色、制作人员是可导航的关联对象，不应只存一段资料表文字。
- [Bushiroad Music 入口](https://bushiroad-music.com/musics/) 先按企划作品与艺人浏览，再进入具体商品。其 [BRMM-11112 商品页](https://bushiroad-music.com/musics/brmm-11112/) 同时列出两种 Blu-ray 限定盘：A（BRMM-11112）与 B（BRMM-11113）共用两首 CD 曲目，但 BD 分别收录台北和东京的演出，封入卡与店铺特典也因版本、渠道而异。这是“同一音乐项目、不同发行内容”的直接样本。
- [BRMM-11089 商品页](https://bushiroad-music.com/musics/brmm-11089/) 同页列出通常盘 BRMM-11090、附立牌的初回限定盘 BRMM-11089、五首 CD 曲目、不同售价与店铺特典。两个品番是两个发行版本；立牌和店铺赠品不应伪装成 CD 曲目。

## 2. 当前架构的边界

目录的固定骨架是 `Work → ContentUnit → Expression` 与 `Release → Medium → Track → TrackContent`；两支由 `Release.subjects → Work` 连起来，而不是一个 Release 只能属于一个 Work。`TrackContent` 引用 Expression，允许一个录音在单曲和多张专辑的不同轨位复用。数据库对篇目同 Work、载体同 Release、轨位同 Medium 的父子关系有复合外键，目录核心关系另存在 `catalog.relations`；证据见 `backend/migrations/000001_catalog_core.up.sql` 的 `content_units`、`expressions`、`mediums`、`tracks`、`release_subjects`、`track_contents`、`relations`。

这些层级有不同的身份，不能用“版本”一个字段代替：Work 是作品身份，ContentUnit 是作品内部稳定单元，Expression 是具体创作或剪辑表达，Release 是对公众发布的产品或版本，Medium 是 CD、BD、黑胶、纸册或数字承载，Track 是该载体内的位置。每个简单作品只需实际存在的层级。

当前 definitions 已提供专辑、歌曲、小说、动画、电影等动态类型；发行的版本类别、发行批次、地区、渠道、品番与包装；载体的 CD、BD、DVD、黑胶、纸册、数字/Web 格式；封装附件、店铺特典、事件等结构字段。定义及四语名称来自服务端并支持后台草稿、差异检查与发布，入口是 `/admin` 的 DefinitionsEditor。**可扩展的是业务类型、字段、词表、关系规则与模板；八种固定实体骨架及外键约束仍需代码和迁移修改**。这是刻意的完整性边界，应在后台明确提示。

## 3. 各类内容的建档和用户展示

| 类别 | 建档例子 | 用户页面应说明什么 |
| --- | --- | --- |
| 专辑多版本 | 以 BRMM-11089 页为例：迷你专辑 Work；通常盘 BRMM-11090、附立牌限定盘 BRMM-11089 各一 Release，都有 CD Medium 和五首实际曲序，立牌只属于限定盘的附件。若另有台版，地区、品番和收录不同就在该 Work 下另建 Release。 | 专辑页汇总各版；版本对比按发行、载体、曲序和特典逐层显示差异。商品页首先说明本版实际包含什么，不能仅展示“限定版”标签。 |
| 同单曲的不同 BD 特典 | BRMM-11112 页是双乐队 split single，A、B 两种限定盘各有一张 CD 和一张 BD，CD 曲目相同，BD 则分别收录台北和东京演出。各版 Release 的 BD Medium 下各建相应 Track，指向不同演出影像 Work/Expression，并把这些 Work 列入各版 subjects。 | 两版可以共用歌曲/录音身份，但 BD 内容不能合并成一张“特典盘”。版本对比应突出影像内容、封入卡和店铺特典差异。 |
| 单曲与跨专辑收录 | 歌曲《甲》自身是 Work，其录音室录音为 Expression。单曲 CD 发行、专辑 CD 发行及精选集黑胶发行分别有自己的 Release/Medium/Track；三个 TrackContent 引用同一个 Expression。若黑胶有新母带，另建 Expression 并用现有 `revision_of` 或后台定义的 `remaster_of` 说明；作品身份仍可相同。 | 歌曲页显示“出现于”哪些发行及盘面/轨号；专辑页显示本版收录的具体录音。用户能从 Track 回到歌曲 Work，同时保留发行轨位。单曲作为商品的发行与歌曲作为作品应有不同链接和标题。 |
| 小说与章节 | 小说 Work 下建立“第一卷/第三章”等 ContentUnit 父子树；日文原文与中文译文为关联该章节的 Expression。日文文库版、繁中平装版分别是 Release，纸册 Medium 内的 TrackContent 用 `locator.page_start/page_end` 记录本版页码。 | 作品页展示章节树和可选语言；版本页展示本版目录、页码、译者与 ISBN。页码属于载体定位，不应写回章节实体。 |
| 动画剧集 | 以 Bangumi 条目为例：这一季是 Work，第 78–85 集为 ContentUnit，逐话首播日期属于相应单元。WEB 原版与有内容差异的 BD 修订为 Expression；网络发布、BD 盒装、DVD 版分别是 Release，盘或数字集为 Medium，轨位映射到相应集的 Expression。角色用 `character_in`，导演/编剧等用关系或结构化署名。 | 作品页有章节、角色、制作人员、关联入口；各版展示实际收录的集数、顺序、剪辑差异、字幕/语言。未公布的单集题名不得补猜。 |
| 电影及文件版本 | 电影 Work 可不建章节；院线剪辑、导演剪辑分别是 Expression。正式 WEB、BD、DVD 产品分别建 Release 和 Medium。某份 WEB-DL 或 REMUX 文件是存储资源和来源/技术特征，只有其对应真实公开发行时才建目录 Release。 | 作品页对比不同剪辑与发行；发行页说明载体、地区、语言及实际内容；文件下载卡由存储服务按权限提供，不把资源编码当成新作品。 |

跨 Work 的收录必须把相关作品声明在 `Release.subjects`，否则目录的 `undeclared_release_subject` 会拒绝。纯立牌、随机卡等实物可放在发行的 `attachments`；按店铺或购买条件变化的赠品放 `store_bonuses`。有独立可编目内容的赠 BD/CD 才应建立 Medium、Track 和 Expression。二者可以同时存在，例如“限定盘含 BD 与随机角色卡”。

## 4. 可编辑关系和后台扩展的约束

后台应允许管理员在 GUI 增删改关系定义的四语名称与反向名称、允许的源/目标 kind、附加字段、显示分组、署名槽位、是否计入署名、是否聚合、无环/对称语义，再以草稿预览、影响检查、发布流程生效。编目者再用关系编辑器给实体连边。这样新增“导演”“改编自”“主题曲用于”一类关系无需改代码；关系端点合法性、同域归属、循环拒绝和数据库外键仍由核心保证。

字段和词表同样走 GUI，但要区分**定义扩展**与**结构变更**：后台新增“地区代码”“音声规格”字段不要求迁移；新增第九种固定骨架、允许 Track 跨 Medium、改变 TrackContent 的主键等会影响不变量，必须走设计审查、迁移与回归。管理员不应被告知“任何结构都能零代码修改”。

建议把“这个关系用于署名还是创作关系”“是否显示为作品组成”直接作为 GUI 可见设置与帮助文案；发布前给受影响实体数、字段不兼容项和回滚目标定义版本。关系重复判定应以端点、类型和属性为身份，`position` 仅表示顺序，不能用排序值制造重复边。

## 5. 用户前端的现状与改进顺序

现有用户前端并非空白：`WorkContentDirectory` 已显示章节/表达与聚合关系，发行详情有同作品版本切换、多 Medium 曲目和反向收录，Medium 详情可从 Track 跳到 Expression，后台 DefinitionsEditor 可配置关系的源/目标、四语名称、分组及校验语义。本轮修复了 definitions 异步加载后聚合目录未重算的问题（`frontend/src/components/work/WorkContentDirectory.tsx`）。下面是进一步优化的验收顺序，不应把已有能力重复开发一遍。

1. 作品页以“作品内容 → 发行版本 → 参与者/关联”的顺序导航。单曲、专辑、章节、动画单集使用同一套层级规则与各自模板；不把所有类型塞进一张平铺资料卡。
2. 发行页把每个 Medium 作为盘/册/数字集单独显示，Track 显示编号、题名、表达版本与可点击作品链接；对 BD 附赠、双 CD、黑胶 A/B 面与书籍页码使用同一个树形结构。缺少结构数据时显示“尚未编目”，不从标题推断曲目。
3. 版本对比先对齐 Release，再按 Medium 和 TrackContent 对齐，分清“同一录音换了轨位”“换了录音/剪辑”“额外 BD”“仅包装/店铺特典不同”。字段标签从 definitions 解析四语名称，不显示原始代码。
4. 作品页提供从歌曲 Work 反查单曲、专辑、精选集的发行入口；动画/小说页面提供章节树及子单元详情入口。关系页保持可筛选的角色、制作人员与创作关联，关联对象有链接。
5. 编辑流程给管理员与编目者明确区分：定义管理决定“可填写什么”，实体编辑决定“这件作品是什么”。Release 保存前检查 subjects 与实际 TrackContent 指向的 Work；编辑现有实体时提示 PUT 是整组替换，保存后回读。

截至 2026-09-23，本批补齐了上述三个缺口：

- `GET /api/catalog/releases/{id}/toc` 在同一只读快照中聚合 Release、Medium、Track、可见 Expression 与定义版本；发行页和载体页复用该接口，旧实例返回 404 时暂时回退原有读取路径。
- 发行用途词项新增可选 `is_bonus`，Definitions GUI 可逐项控制附赠分组。种子对旧定义只回填缺失标记，显式 `false` 保留。
- Scheme 新增 `medium_formats`，曲目定位可依据所属 Medium 的定义格式词表匹配。GUI 可编辑该约束；载体格式变更会回放其曲目并拒绝违反新规则的保存。

版本仍按“专辑 Work / 各发行版 Release / 实际 Medium 与 Track / 可复用 Expression”表达；小说章节继续使用 ContentUnit 与 Expression。固定八实体骨架、结构外键和数据库约束仍需代码与迁移变更，业务类型、字段、词表语义、关系和展示方案继续由 Definitions GUI 管理。

线上版本和数据补录以部署验收记录为准。封面与简介覆盖率仍是实际数据质量缺口；候选条目只依据官方来源补录，不以自动生成或来源不明图片填充。

## 6. 服务拆分与技能文档

目录服务保有实体、定义、版本、关系、修订与搜索语义；账号服务保有身份和令牌；互动服务保有评论、论坛、收藏；存储服务保有文件、哈希、绑定和下载。用户前端可以经同源网关组合数据，但各服务应只写自己的 schema，跨域通过稳定实体 UUID、HTTP 契约和幂等事件协调。对本需求，**不要按音乐/小说/影视再拆目录微服务**：这些内容共享同一作品身份、发行与关系图，需要一致的校验和查询。

当前拆分并不等于独立部署完成。各服务共享 PostgreSQL 实例、同源网关和主仓编排，主仓用户前端仍组合社区、账号、存储能力。这对当前规模是可接受的渐进拆分，但要把可用性、版本和回滚视作跨仓契约问题：

| 现状及风险 | 建议与验收 |
| --- | --- |
| `deploy/nginx.conf` 是路由矩阵生效源，多个服务的路径在同一网关汇合；错分流会让“接口存在”变成用户 404。 | 路由矩阵保持一个生效源，CI 比对各服务 OpenAPI/路由、网关和主仓登记表，发布时用版本锁核对各进程身份。搬仓本身不是目的，防漂移才是验收。 |
| 主仓用户前端调用多个服务，某服务字段变化可能触发主前端重发；三服务已有独立管理台，账号已有独立登录应用。 | 先稳定 API 与可嵌入区块的契约，再按实际发布频率迁移页面。统一导航、会话、四语词条和无障碍体验要跨应用验收；不应仅为了“每服务自带 UI”复制整套前端 shell。 |
| `catalog.outbox` 有合并事件，但跨服务消费者尚未闭环；历史 ID 的收藏、文件绑定等引用需要可预测的收敛。 | 先定义消费者幂等、重放、死信/积压告警和 canonical ID 解析，再切异步；验收包含 A→B 合并后社区与存储的读取、写入、重试。同期保留同步查询的正确性。 |
| 迁移、种子、启动职责曾在不同服务不一致；网关回滚无法自动撤销数据库及切流后的写入。 | 逐服务统一“迁移由 owner 执行、应用启动只校验”的目标；每次回滚先检查旧镜像处理器、schema 兼容性和新写入。目录服务已采用显式 `mf-migrate`，其他服务按各自实际路径核对。 |

因此优化顺序是：先稳定路由与发布契约、聚合查询和合并身份；再按服务划分用户页面；最后再考虑 SDK 复用和部署形态升级。不要靠复制目录实体表或跨 schema JOIN 解决页面展示。

`backend/migrations/000001_catalog_core.up.sql` 的文件头仍保留早期“HTTP 启动执行 DDL”的表述，但迁移器对已执行文件逐字校验 checksum（`backend/internal/migrator/migrator.go`），因此不能为修文字改动该文件。当前 HTTP 启动只调用 `CheckCompatibleVersion`（`backend/cmd/server/main.go`）；`Store.Initialize` 的建库路径只供本地安装与测试。本文和拆分契约记录现行行为，迁移文件作为已执行历史保持原文。

编目技能应只记录实际可执行的编目流程、证据规则与模型边界；完整 API 字段说明由文档站和 OpenAPI 负责，服务拆分/部署状态归架构文档。技能中发现的过时端点、网关归属和“专辑曲目一定是 ContentUnit”这类绝对化表述，应按当前契约修订；同一歌曲跨专辑的稳定身份是 Work，实际每版曲序是 Track，二者不能互相替代。

## 7. 验收样本

上线前以隔离数据造五组可回读样本：① 同 CD 不同 BD 的 A/B 盘；② 同歌曲录音在单曲、专辑、黑胶三种发行中出现；③ 原文/译文章节在两种纸版页码不同；④ 动画各集在 WEB、BD、DVD 收录及角色/署名关联；⑤ 从后台新建一种四语关系，发布后无前端发版即可编辑、显示、筛选。每组检验 API 写入与回读、详情与对比、四语、窄屏和键盘操作；权限分别覆盖匿名、普通贡献者与管理员。样本中的产品事实附来源，假设场景明确标注，不把测试造数当成真实编目。
