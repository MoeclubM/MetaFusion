# 元数据身份与层级关系演进方案（提案）

> 状态：待评审的架构提案，2026-09-25。本文不改变现行写入契约或已发布 definitions。若决定实施，先同步更新[架构基准](./spec-driven-requirements.md)，再按阶段修改数据库、API、管理台和用户界面。

## 1. 要解决的问题

MetaFusion 要记录作品、内容、表达、发行及其关系，同时避免三类失真：同一事物因平台或版本不同而重复建实体；把发行收录误当成父子归属；在没有数据时展示空目录，或把取数失败说成没有内容。

当前八种 kind 是有约束的身份骨架。业务类型、字段、词表、普通关系和展示模板来自 definitions；`definitions.structure` 对现有结构只作描述，发布校验要求它与固定外键一致。实际归属由 `content_units`、`expressions`、`mediums`、`tracks` 的侧表和外键保存；`release_subjects` 与 `track_contents` 是多对多收录引用；`catalog.relations` 保存署名、创作、聚合等语义关系。现状详见[媒体编目复核](./media-catalog-frontend-review-2026-09.md)和[目录核心实现](./catalog-core-implementation.md)。

本方案的目标是让**新业务层级的关系规则可声明、可校验、可查询**，保留已有结构的完整性。它不把八种身份随意改名，也不把目录变成无类型的通用知识图谱。

## 2. 先决定“记录什么”

| 记录方式 | 判断标准 | 例子 |
| --- | --- | --- |
| 实体 | 有持续身份，可独立修订、引用、合并，或被多个记录复用 | 游戏 Work、某条路线 ContentUnit、实际发行 Release |
| 属性 | 是某实体的标量或小型结构，通常不需要独立生命周期 | 首发日期、语言、时长、品番 |
| 词表项 | 需要统一取值和四语名称，但暂不需要独立事实与关系 | 载体格式、图片用途、发行用途 |
| 结构关系 | 表达归属、导航位置或带顺序的收录，改变它会改变目录结构 | 章节属于作品、轨位属于载体、轨位收录表达 |
| 语义关系 | 两端各有独立身份，连接不改变任一端的所有权 | 配乐用于游戏、改编自、演员出演角色 |

建档时先查外部 ID、已有合并重定向、同作品下的稳定标识和来源；标题相近只产生待核对候选，不自动合并。译名、平台、介质、销售地区或修订日期本身不构成新 Work。内容确实变化时才考虑新的 Expression；公开产品或发行条件变化时考虑 Release；只有可独立编目的组成创作才建另一 Work。不能为填满层级而造空 ContentUnit、Medium 或 Track。

## 3. 关系规则分层

“关系动态”指管理员能声明合法端点与约束，写入与读取遵循同一份已发布规则；不等于允许任意两点相连。规则分为四类，关系码及所属类别发布后不可改义，改义须新建码并迁移旧边。

| 类别 | 语义与基数 | 现有事实来源 | 扩展方式 |
| --- | --- | --- | --- |
| `ownership` 归属 | 子实体有一个确定的直接所有者；决定域和生命周期 | `content_units.work_id`、`expressions.work_id`、`mediums.release_id`、`tracks.medium_id` | 现有四项继续由外键负责；确认出现新形状后用受约束的扩展边 |
| `placement` 定位 | 在已归属的域内挂到目录父节点，可排序且不得成环 | `content_units.parent_id`、`expressions.content_unit_id`、`mediums.parent_id`、`tracks.parent_id` | 新定位规则须声明共同域、父子种类和无环范围 |
| `inclusion` 收录 | 引用独立对象，不取得其所有权；可多端、带次序及定位 | `release_subjects`、`track_contents` | 现有两项保留专用约束；新收录形状使用受约束的扩展边 |
| `semantic` 语义 | 署名、创作、聚合、从属等，不改变结构所有权 | `catalog.relations` | 沿用动态关系定义、端点白名单和版本流程 |

例如 Release 的多个 subjects 不是多个“父 Work”；专辑 Track 引用歌曲的 Expression，也不把歌曲 Work 移到专辑之下。`includes` 等聚合语义不能同时伪装成已有的 `work_id` 或 `parent_id`。同一关系只建一个有方向的码，反向用定义里的 `reverse_names` 展示，不再另建同义反向码。新码发布前须检查现有码的同义、包含及逆向关系，并附正例和反例。每种事实由**一个权威存储适配器**负责，统一图谱 API 可以汇总展示，但不建立第二套可独立编辑的副本。

## 4. 动态结构规则的边界

新增规则在 definitions 中声明稳定码、四语正反向名称、类别、源和目标 kind/type、启用状态及展示分组。结构类别再声明：

- 基数：每个子节点最多几个父节点、每个父节点可有几个子节点；`ownership` 默认每个子节点恰有一个所有者。
- 域：是否必须属于同一 Work、Release 或 Medium；域由现有所有权链解析，不能只比较标题或类型。
- 排序与唯一性：是否有 position、同一容器下的次序是否唯一、同一端点组合能否重复。
- 无环与层级深度：对声明的关系集合检查，而非只检查单个关系码；明确禁止自连。
- 附加字段及来源：字段来自 definitions，关系修订保存证据；需要逐条事实溯源时把来源绑定到该边，而不只依赖一次实体修订的来源列表。
- 生命周期：端点合并时怎样重定向与去重；停用定义只阻止新写，不让历史边凭空消失。

Definitions 草稿、影响预演和发布必须覆盖既有边。缩小端点范围、基数、域或无环规则时，先列出冲突边并拒绝直接发布；关系码不复用，保留定义版本以解释旧修订。定义文档只允许有限的规则字段，不能保存任意 SQL、脚本或前端表达式。跨路径约束（如 TrackContent 指向的 Work 必须属于 Release.subjects）继续由明确的服务端校验器承担。

扩展边建议用 `catalog.structure_links` 保存 `id / rule_code / parent_id / child_id / position / attributes / version`，两端有实体外键，并为端点及规则建立索引。数据库约束兜底端点存在、基本唯一性和非负顺序；作用域、动态基数、跨关系无环由与现有写事务一致的服务端规则引擎校验。不要先把现有外键整批搬进新表：现有外键仍是四条核心归属的权威来源，新表只接受尚无专用事实来源的新形状。内部规则登记标明每个码的唯一存储适配器，编辑入口按规则只写一个来源；对外 API 只暴露业务语义，不暴露表名或适配器。

如果今后确有充分样本要求更改四条核心归属，另立迁移决策：先回填、核对，再切换权威写入和读取；旧列只由权威数据投影，不能与新边分别编辑。完成一致性和回滚验证后才移除旧列。不能长期保留两套独立事实。

## 5. 对外读取和界面

提供统一的关系读取契约，返回边类别、方向、关系定义版本、端点、顺序、附加字段及来源，并按用户可见权限过滤。现有实体字段和发行目录 API 继续兼容；新读取层通过适配器读取外键、两个收录表、普通关系和扩展边。列表按容器分页，避免客户端遍历整棵树。

详情页的栏目声明只包含受支持的数据提供者、顺序及显示策略。服务端按同一可见性口径返回栏目数量与状态：`有内容 / 已确认待编目 / 不适用 / 读取失败`。公开页默认只显示有内容的目录；编辑入口仍允许补录；失败时提供重试而不显示“暂无目录”。内容单元、表达版本、组成作品、发行收录各有清楚名称，不能都算作“作品内容目录”。栏目提供者是受控代码集合，模板不能执行任意查询。

## 6. 分阶段实施与验收

| 阶段 | 交付与退出条件 |
| --- | --- |
| A. 语义盘点 | 列出现有外键、收录表和普通关系的唯一事实来源；用游戏、动画、小说、多版本专辑、跨作品盒装各做一组带来源样本，判定哪些现有结构已经足够。 |
| B. 页面与导入修正 | 空目录按实际数据隐藏，取数失败独立呈现；通用“游戏”不再自动映射为“独立游戏”。有路线的游戏仍能显示目录。此阶段不改库结构。 |
| C. 统一关系契约 | 在 definitions 增加关系类别与结构规则的只读登记，为现有外键/收录表实现读取适配器；管理台显示规则和真实约束，普通关系继续按原路径写入。新旧读取结果逐项一致。 |
| D. 扩展结构写入 | 仅为已确认无法用现有结构关系表达、但端点仍有合法身份的形状建立 `structure_links` 写入与编辑器；发布影响检查、事务校验、合并处理、审计和反向查询完整接入。旧结构不复制进去。若端点本身不属于八种 kind，须先单独设计身份和迁移，不能只加一条边。 |
| E. 评估核心迁移 | 只有多个真实样本要求改变核心所有权时才启动；执行回填核对、单向权威切换、兼容投影与回滚演练。若无该需求，保留外键。 |

每阶段都要覆盖四语定义、权限过滤、历史定义版本、关系去重、循环和跨域拒绝、合并后的重定向，以及 `Release.subjects` 与 `TrackContent` 的一致性。验收结果以目标实例的已执行迁移、实际 API 回读和处理器为准，不能用 proposal 文案替代运行事实。

## 7. 游戏实例的目标编目

《NieR:Automata》保留一个 Work；不同公开产品按依据建立 Release，实际承载形态建 Medium。确有稳定身份且有来源的路线、章节或任务可作为该 Work 的 ContentUnit，并用类型和同域父子关系组织；内容有实质差异时再建 Expression。配乐作品是独立 Work，通过 `soundtrack_of` 相连。没有可见内容单元时不展示空目录，不凭游戏类型推断路线。平台若只用于筛选，可先用受控字段；只有需要独立身份、历史和多种关系的真实样本出现后，再讨论新增平台实体，避免为每个词造节点。
