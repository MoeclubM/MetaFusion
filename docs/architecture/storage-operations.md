# 资源存储运行约定

资源文件、哈希和实体绑定由资源模块管理。目录实体保存作品、表达与发行元数据；ISRC、MBID 是内容身份标识，文件 SHA-256 不应作为录音或作品身份。

## 部署与持久化

- 主栈 `deploy/docker-compose.yml` 使用 `ARCHIVE_S3_*` 连接 RustFS。endpoint 为 `host:port`，TLS 单独配置；初始化私有 `metafusion-master` 桶成功后才启动后端。
- `ARCHIVE_PATH=/app/module-data/archive` 挂载 `catalog_archive` 命名卷，用于上传临时文件及媒体预览。元数据栈也持久化该目录，未配置 S3 时作为本地对象存储。
- 若修复前已在旧容器可写层上传资源，部署前必须先备份旧 `module-data/archive` 并核对数据库中的资源哈希。新增卷不会自动迁移这些对象，直接重建旧容器可能丢失文件。该步骤需由运维单独执行。
- 主栈改为 S3 后也不会自动迁移旧本地对象；既有资源应先迁移、按哈希核验，再切换存储配置。

## 上传、下载与预览

现有上传接口经后端接收并计算哈希，按哈希保存对象。请求上限为 1 GiB，不依赖客户端声称的哈希认定文件内容；网关关闭请求缓冲，避免额外写入网关临时磁盘。

下载继续走 `/api/archive/resources/:id/content`。预览走 `/api/media/jobs/:id/preview`，检查资源可见性后返回。废弃的 `/storage/preview/` 返回 404，不直代私有桶，也不将私有预览标成公共缓存。

目前没有需要零拷贝直传、BT Tracker 或分享率治理的已确认需求。它们是独立产品能力，不作为修复现有上传与审计流程的前提。现有完整修订快照也不因缺少差量存储而失效。
