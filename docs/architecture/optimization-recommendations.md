## 1. definitions 生命周期

### 1.1 现状

- 种子播种仍是"空库全量播种"：`catalog.definitions` 非空时不覆盖既有文档，后台改过的关系/词表/字段（如停用某个关系码、词表项降级）全部保留；播种在 `Store.Initialize`（`backend/internal/catalog/store.go`）。
- 新增**启动时只增不改的增量合并**：`Store.EnsureSeedDefinitions`（`backend/internal/catalog/definitions.go`）在播种后调用 `mergeSeedDefinitions`（`backend/internal/catalog/defaults_merge.go`），把种子里新增而当前缺失的键补进已发布文档。
- 新增显式运维入口 `mf-migrate seed`（`backend/cmd/migrate/main.go`），部署后单独确认模板是否已更新；服务启动时执行同一次合并。
- 合并规则（只增不改、可重复执行）：

| 合并动作 | 规则 |
| --- | --- |
| 补缺失顶层键 | 七个分区（`types` / `fields` / `vocabularies` / `relations` / `templates` / `schemes` / `structure`）逐键比对，当前缺失才补 |
| 补缺失子项 | 分区内缺失的类型、字段、词表与词表项、关系码、模板、方案、结构规则按种子补齐 |
| 开关类只打开 | 种子声明为真的附加标记（当前为 `relations.*.aggregate`）仅在"种子为真、当前为假"时补上；种子为假时不动——那可能是后台有意关掉的 |
| 已存在的一律保留 | 键已存在即整条原样保留，不比较、不覆盖字段内容 |
| 审计留痕 | 以系统身份起草并发布，说明里列出本次补入的键（形如 `types.<code>`、`relations.<code>.aggregate`） |
| 幂等 | 无新增时不写库，避免每次启动多出一个定义版本 |

- 版本状态与发布语义：`draft → published → superseded` 三态（`backend/internal/catalog/schema.sql`、`Store.Draft` / `Store.Publish`），发布是整份文档替换；`Store.DefinitionVersions` 返回最近一批版本；`Draft` 要求 `base_version` 等于当前 published，否则 `version_conflict`。

### 1.2 问题

1. **没有定义审计面板**：后台只看到版本记录，看不到"这一版比上一版多了/改了/少了哪些键"；自动合并留下的 `added` 列表埋在审计说明的自由文本里，复核要靠下载两份 `document` 手工比对。
2. **没有回滚到指定版本**：回到历史版本只能人工取出该版 `document` 再起草一次；状态机没有回滚语义，误发布或合并结果不合预期时恢复成本高。
3. **字段级修正不在合并范围**：改名、改口径、改字段类型、停用词表项仍要在设计器里人工逐条操作。
4. **"漏合并"与"有意删除"不可区分**：`mergeSeedDefinitions` 只按"当前缺不缺这个键"判断，无法识别某键是后台有意删除还是种子新增未达。
   注：把 `Enabled=false` 之类当作"缺失"会破坏"只增不改"（覆盖后台有意关闭的决定），因此不在建议范围内。

### 1.3 建议做法

| 方向 | 做法 |
| --- | --- |
| 定义版本可视化（含 diff） | 版本列表按"与上一版 / 与指定基线"输出字段级差异条目，路径用键路径表达（如 `relations.<code>.aggregate`、`fields.<field>`），覆盖新增、删除、值变更、开关翻转四类 |
| 一键回滚 | 选定历史版本 → 生成新草稿（`base_version` = 当前 published）→ 走既有 `impact` → `publish`，不原地改历史状态；状态机可评估补 `rolled_back` 标记或复用 `superseded` |
| 开关类修正走自动合并 | 把可自动补充的"打开能力"类标记收敛成显式白名单（当前为 `aggregate`），白名单外的一律不动；新增标记必须同时补测试 |
| 改语义走显式迁移 | 改名、改口径、改字段类型、删除键等语义变更携带唯一迁移标识与影响预演结果，禁止由合并路径自动执行 |

### 1.4 已落地部分

种子增量合并（`EnsureSeedDefinitions` + `mergeSeedDefinitions`）与 `mf-migrate seed` 已可用，只增不改且幂等。

### 1.5 待办

| 待办 | 可验证的完成判据 |
| --- | --- |
| 版本列表带字段级 diff | 接口按版本返回差异条目（含键路径与变更类型）；单测覆盖"新增键 / 删除键 / 值变更 / 开关翻转"四类输出；后台面板不下载 `document` 即可显示差异 |
| 一键回滚到指定版本 | 存在"从指定历史版本起草"的入口；单测断言：以历史版本 `<ver>` 起草并发布后，`Store.Definitions` 文档与该版本文档逐键相等，且审计说明记录目标版本号；`base_version` 不匹配时返回 `version_conflict` |
| 自动合并白名单化 | `mergeSeedDefinitions` 单测覆盖三条：种子真/当前假 → 补上并进入 `added`；种子假/当前真 → 值不变且不进 `added`；同输入连续合并两次，第二次 `added` 为空 |
| 语义修正是显式迁移 | 语义类变更必须携带迁移标识与预演结果；缺标识时合并路径拒绝写入（错误码可在测试中断言），自动写入只发生在新增与开关白名单内 |

## 2. 多源导入优先级与字段级来源留痕

### 2.1 现状

- 来源优先级是**人工约定**：按"官网优先、数据库站点补充"的经验判断取值，仓库里没有承载这份优先级的声明。
- 来源落点是**实体级**：每次编目变更带 `edit_note` + `source_urls`（HTTP(S) 地址列表），来源与说明进审计与修订；实体自身的来源线索就是 `source_urls` 与编辑说明。
- 来源站点注册在 `catalog.external_databases`（后台 CRUD），提供站点元信息，但不含"取值优先级"语义。
- 导入预检的错误码族 `importer_mapping_stale:*` 校验的是"代码写死映射是否仍被已发布定义支持"（关系码、词表项、类型），不校验来源与取值优先级。

### 2.2 问题

1. **优先级不可复核**：同一字段被多个来源给出不同值时，谁覆盖谁只存在于执行者的记忆与说明里，评审者无法从数据反推。
2. **provenance 粒度到实体不到字段**：`source_urls` 是一个地址列表，回答不了"这个字段的值来自哪个来源"。
3. **被覆盖值不留痕**：按优先级取值后只剩最终值，后续改判（新来源出现、原来源被证伪）没有依据。
4. **同优先级冲突无固定路径**：两个同档来源给出不同值时，处理方式随人而异。

### 2.3 建议做法

| 方向 | 做法 |
| --- | --- |
| 优先级声明化 | 在 definitions（或来源库注册）声明来源档位 `official > database > community`，导入按声明解析取值，不按执行者习惯 |
| 字段级 provenance | 导入时为每个被赋值的字段记录来源标识（来源 code + 来源地址），随实体落库，读接口按字段返回 provenance |
| 冲突按优先级取值 | 同字段多源冲突按声明优先级取值；低优先级值不丢弃，作为"被覆盖值"保留在属性或修订快照中 |
| 同档冲突 | 不自动取值，标记为待人工裁决项并在预检结果里列出 |
| 与现有落点并存 | `source_urls` / `edit_note` 继续作为实体级证据保留；字段级 provenance 是更细一层，不替代实体级证据 |

### 2.4 已落地部分

实体级来源与编辑说明已是写入路径的强制项，来源库注册后台可维护，导入预检已把"载荷映射过期"提前到零写入阶段。

### 2.5 待办

| 待办 | 可验证的完成判据 |
| --- | --- |
| 来源优先级声明 | 优先级可从已发布 definitions（或来源库注册）读取；单测断言：同字段两源冲突时，取到的是声明档位更高的一方，且顺序改声明后取值随之改变 |
| 字段级 provenance 落库 | 导入后读回实体，能按字段得到来源标识；无来源的字段在 provenance 中显式缺省而非默认填充；契约文档与 DTO 同步声明该字段 |
| 被覆盖值保留 | 冲突场景单测断言：最终值来自高优先级来源，同时低优先级值可在属性或修订快照中读回 |
| 同档冲突转人工 | 预检或导入结果返回待裁决条目清单；列表为空时才允许静默完成导入 |

> 说明：当前"来源声明"是自由文本，字段级 provenance 尚无结构化承载——本节建议是从零建立这层结构，不是在既有字段上改名。

## 3. 数据完整性自检

### 3.1 现状

- 检查靠人工写 SQL 抽查，加上导入预检：`importerPreflight`（`backend/internal/catalog/importer.go`）在写库前只读校验整份载荷（章节树拓扑、显式表达引用、字段码归属、写死映射是否过期），失败即零写入。
- `definitions.structure` 已能声明各层级的结构归属：结构字段、允许作为目标的层级、是否必填、候选按哪个字段过滤（`StructureRule` / `StructureField`，`backend/internal/catalog/types.go`），校验与编辑器共用这份声明。
- 尚无固定的完整性检查命令或定时任务，也没有报告产物与基线，检查口径散落在个人 SQL 里。
- 关系码失效在读路径上是宽容的：`relations` 读取时校验失败静默跳过，表现为"读不到"而不是报错。

### 3.2 问题

1. **检查项不固化**：口径在个人手里，换人重写 SQL，结果不可比。
2. **覆盖面不成清单**：缺父级、缺翻译、缺图片、关系码缺失、同域父节点异常、来源缺失等没有统一入口。
3. **层级知识会被重复实现**：不消费 `structure` 声明的检查脚本必须自己写一套"哪个层级该挂哪个层级"的规则，与写入校验各说各话。
4. **无报告与趋势**：只有一次性查询结果，没有可留存、可比对的产物。

### 3.3 建议做法

固化为只读命令（`mf-migrate check` 一类子命令）+ 定时任务，输出机器可读报告（JSON）与人读摘要表；检查项以 definitions 为基准，能复用 `structure` 的不另写层级知识：

| 检查项 | 口径（基准） | 严重级 |
| --- | --- | --- |
| 缺父级 | `structure.<kind>` 中 `required` 为真的结构字段为空 | 阻断 |
| 同域父节点异常 | 父节点 kind 不在 `StructureField.TargetKinds` 内（`target_kinds` 为空表示同层，即同域） | 阻断 |
| 层级不满足 | 实体的实际结构不满足 `structure.<kind>` 声明（如表达未挂作品、载体未挂发行） | 阻断 |
| 关系码缺失 | 关系的 `type` 不在已发布 definitions 中，或该码已停用 | 阻断 |
| 缺翻译 | 必备语种缺题名或摘要 | 警告 |
| 缺图片 | 无封面且无官方图标记 | 提示 |
| 来源缺失 | 实体无 `source_urls` 且其修订无来源记录 | 警告 |

- 检查只读、不改数据；失败不阻塞写入口，由运维按报告决定处置。
- 报告字段固定（检查项、严重级、命中数量、样例标识列表），报告本身可进 CI 产物或部署留档，便于跨时间比对。
- 第 2 节的字段级 provenance 落地后，"来源缺失"细化到按字段判定。

### 3.4 已落地部分

导入预检已实现零写入前置校验（含映射过期），`structure` 声明已驱动写入校验与编辑器渲染。

### 3.5 待办

| 待办 | 可验证的完成判据 |
| --- | --- |
| 只读检查命令 | 命令可在不写库的前提下运行并输出固定字段的报告（含每项检查命中数量）；构造缺父级、同域父节点异常、关系码缺失三类夹具时，报告分别命中且严重级正确 |
| 复用 `structure` 判定 | 单测断言：修改 `structure` 声明（如把某结构字段改为必填）后，检查结果随之变化，且不需要改检查代码 |
| 定时任务与留档 | 检查以固定周期执行并落档报告；两次报告可比对（按检查项给出数量变化） |
| 关系失效边显式化 | 读路径静默跳过的非法边在检查报告中列出（含边标识与原因），不再只体现为"读不到" |

## 4. 前端外壳组件化

### 4.1 现状

- 页签动画已统一：`.mf-tabpanel`（`frontend/src/app/globals.css`）只挂在面板/列表容器上，且必须让容器 key 随切换源变化才会重放；详情页、社区列表与帖子页、探索页、管理台已接。
- 头部高度令牌 `--mf-header-h` 统一顶部偏移（各页粘性定位用它计算），主题令牌（surface / line / text 系）与密度口径（区块内边距、区块间距、标题分隔线）本轮已统一。
- 各页仍**自写宽度与内边距**：`max-w-*` / `px-*` / `py-*` 散落在首页、探索、社区、详情、发行/载体、管理台等页面与组件中。
- 探索页已把层级树、类型下拉这类硬分类换成标签驱动：类型筛选项由 `definitions.types` 计算，标签云来自真实的聚合标签，骨架只保留固定 kind 的分层分组，类型作为卡片徽标与搜索条件呈现。
- 共享组件只有 `frontend/src/components/ui`（Modal、Select）与 `frontend/src/components/common`（封面相关），没有页面壳、页签面板、卡片、区块标题这四类外壳。

### 4.2 问题

1. **布局口径无法一处调整**：颜色已走令牌，宽度与内边距仍按页面各写一套，密度调整必须逐页改、逐页验。
2. **新页面靠复制**：没有页面壳，新建页面只能照抄某个已有页面的 `main` 包装与容器宽度，口径随复制源漂移。
3. **写死的类型知识仍有残留**：本轮已把结构归属区、资源分节、导航入口改为按 definitions 渲染，但其它页面与组件仍存在按 kind/type 分支的渲染与固定映射，新增类型或层级时仍可能要改前端。

### 4.3 建议做法

| 组件 | 职责 | 页面不再自写 |
| --- | --- | --- |
| PageShell | 最大宽度、水平内边距、纵向间距、主区包装 | `max-w-*`、`px-*`、`py-*` |
| TabPanel | 页签容器：挂动画类并按切换源重挂载 | 动画类名与容器 key 逻辑 |
| Card | 卡片圆角、边框、背景与内边距 | 卡片 `p-*` 与边框/背景组合 |
| SectionTitle | 区块标题排版与分隔线密度 | 标题字号与分隔线内边距 |

- 规则：宽度、内边距、动画只在外壳组件内定义，页面禁止自写这三类工具类；用一条可自动执行的检查兜住，而不是靠约定。
- 写死的类型知识（层级、类型、字段、词表）改为查 `definitions`（`structure` / `types` / `templates` / `vocabularies`）；声明缺失时报缺口，不在代码里补默认分支。

### 4.4 已落地部分

页签动画类 + key 重放约定、头部高度令牌、主题令牌、密度口径四处已在同一轮统一，探索页已完成标签驱动的筛选改造。

### 4.5 待办

| 待办 | 可验证的完成判据 |
| --- | --- |
| 四个外壳组件落地 | PageShell / TabPanel / Card / SectionTitle 存在于共享组件目录；主要页面改用它们后 `bunx tsc --noEmit` 与 `bun run build` 通过；抽查页面渲染结果与改造前的宽度、内边距一致 |
| 页面不再自写布局工具类 | 新增一条检查：页面目录内出现 `max-w-*` / `px-*` / `py-*` 即失败；落地后该检查在既有代码上全绿（命中只允许出现在外壳组件内） |
| 页签走统一容器 | 所有 tabpanel 容器由 TabPanel 渲染；切换页签时可观测到容器重挂载与动画重放（DOM 节点更换） |
| 硬编码类型知识清零 | 相关映射名与按 kind/type 的固定分支清零；验收方式：在后台新增一个类型或层级声明后，刷新页面即可显示与筛选，不需要改前端代码 |

## 5. 落地顺序与依赖

| 顺序 | 事项 | 依赖 | 说明 |
| --- | --- | --- | --- |
| 1 | 定义版本列表 + 字段级 diff | 无（`DefinitionVersions` 已存在） | 先有可读差异，才谈回滚 |
