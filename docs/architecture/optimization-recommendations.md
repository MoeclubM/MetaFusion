| 小节 | 回答的问题 |

## 1. definitions 生命周期

### 1.1 现状

- 种子播种是"空库全量播种"：`catalog.definitions` 非空时不覆盖既有文档，后台改过的关系/词表/字段（如停用某个关系码、词表项降级）全部保留；播种在 `Store.Initialize`（`backend/internal/catalog/store.go`）。
- **启动时只增不改的增量合并**：`Store.EnsureSeedDefinitions`（`backend/internal/catalog/definitions.go`）在播种后调用 `mergeSeedDefinitions`（`backend/internal/catalog/defaults_merge.go`），把种子里新增而当前缺失的键补进已发布文档。
- 显式运维入口 `mf-migrate seed`（`backend/cmd/migrate/main.go`），可单独确认模板是否已更新；服务启动时执行同一次合并。
- 合并失败**不再致命**：定义非法时零写入失败并返回 `*DefinitionSeedError`，服务保留上一个已发布定义降级启动，`GET /health` 的 `definitions` 块给出 `published_id` / `degraded` / `pending_publish_error`；悬挂引用（存量数据指向不存在的行）只进警告报告。失败留下的草稿按"同内容同 base"复用，重复启动不新增定义行。
- 与之配套的运维入口 `mf-migrate check-refs`：一次列出库里全部悬挂引用（attributes 的 entity 型取值、结构与记录级引用、关系端点与关系属性），有则非零退出，作为部署前置检查（见 [切流手册](./cutover-runbook.md) 的"部署前置检查"一节）。
- 合并规则（只增不改、可重复执行）：

| 合并动作 | 规则 |
| --- | --- |
| 补缺失顶层键 | 七个分区（`types` / `fields` / `vocabularies` / `relations` / `templates` / `schemes` / `structure`）逐键比对，当前缺失才补 |
| 补缺失子项 | 分区内缺失的类型、字段、词表与词表项、关系码、模板、方案、结构规则按种子补齐 |
| 补名称译文 | 名称某语种缺失、或该语种值仍等于英文占位时，用种子译文补上；已有译文一律不动 |
| 开关类只打开 | 种子声明为真的附加标记（当前为 `relations.*.aggregate`）仅在"种子为真、当前为假"时补上；种子为假时不动——那可能是后台有意关掉的 |
| 已存在的一律保留 | 键已存在即整条原样保留，不比较、不覆盖字段内容 |
| 审计留痕 | 以系统身份起草并发布，说明里列出本次补入的键（形如 `types.<code>`、`relations.<code>.aggregate`） |
| 幂等 | 无新增时不写库，避免每次启动多出一个定义版本 |

- 版本状态与发布语义：`draft → published → superseded` 三态（基线结构见 `backend/migrations/000001_catalog_core.up.sql`，`Store.Draft` / `Store.Publish`），发布是整份文档替换；`Store.DefinitionVersions` 返回最近一批版本；`Draft` 要求 `base_version` 等于当前 published，否则 `version_conflict`。
- 管理侧读取与回滚：
  - `GET /api/admin/catalog-definitions`（`include_document=false` 取瘦身列表）、`GET /api/admin/catalog-definitions/{id}`（任意状态单版本）、`GET /api/admin/catalog-definitions/{id}/diff?against=`（字段级差异，条目 = 键路径 + `added/removed/changed/toggled`）。
  - `POST /api/admin/catalog-definitions/{id}/rollback`：读目标版本文档 → 只读 impact 预检 → 以当前 published 为 base 走 `Draft`→`Publish`，不原地改历史行。回滚到当前版本返回 `no_op`。

### 1.2 问题

1. **后台没有定义版本面板**：版本列表、单版本详情、字段级 diff 与回滚四个能力都在接口侧，管理台尚未把它们接成可操作界面；复核版本差异目前只能走 API 或下载两份 `document` 手工比对。
2. **字段级修正不在合并范围**：改名、改口径、改字段类型、停用词表项仍要在设计器里人工逐条操作。
3. **"漏合并"与"有意删除"不可区分**：`mergeSeedDefinitions` 只按"当前缺不缺这个键"判断，无法识别某键是后台有意删除还是种子新增未达。
   注：把 `Enabled=false` 之类当作"缺失"会破坏"只增不改"（覆盖后台有意关闭的决定），因此不在建议范围内。

### 1.3 建议做法

| 方向 | 做法 |
| --- | --- |
| 定义版本面板 | 列表用 `include_document=false` 取数（不下载文档）、点版本才拉 `/{id}`、变更区直接渲染 `/{id}/diff` 的 `changes` 与 `summary`；回滚按钮走 `POST /{id}/rollback` |
| 开关类修正走自动合并 | 把可自动补充的"打开能力"类标记收敛成显式白名单（当前为 `aggregate`），白名单外的一律不动；新增标记必须同时补测试 |
| 改语义走显式迁移 | 改名、改口径、改字段类型、删除键等语义变更携带唯一迁移标识与影响预演结果，禁止由合并路径自动执行 |

### 1.4 待办

| 待办 | 可验证的完成判据 |
| --- | --- |
| 定义版本面板接三端点 | 接口返回差异条目（含键路径与变更类型）；单测覆盖"新增键 / 删除键 / 值变更 / 开关翻转"四类输出；面板打开时列表请求不含 `document`，切换版本不再重复拉全文 |
| 面板内的回滚入口 | 以历史版本 `<ver>` 回滚并发布后，`Store.Definitions` 文档与该版本文档逐键相等，且审计说明记录目标版本号；`base_version` 不匹配时返回 `version_conflict` |
| 自动合并白名单化 | `mergeSeedDefinitions` 单测覆盖三条：种子真/当前假 → 补上并进入 `added`；种子假/当前真 → 值不变且不进 `added`；同输入连续合并两次，第二次 `added` 为空 |
| 语义修正是显式迁移 | 语义类变更必须携带迁移标识与预演结果；缺标识时合并路径拒绝写入（错误码可在测试中断言），自动写入只发生在新增、名称补译与开关白名单内 |

## 2. 多源导入优先级与字段级来源留痕

### 2.1 现状

- 来源优先级是**人工约定**：按"官网优先、数据库站点补充"的经验判断取值，仓库里没有承载这份优先级的声明。
- 来源落点是**实体级**：每次编目变更带 `edit_note` + `sources`（每条含 `kind`（`url`/`publication`/`self`）、`citation` 与可选 `url`），来源与说明进审计与修订；实体自身的来源线索就是这两项。
- 来源站点注册在 `catalog.external_databases`（后台 CRUD），提供站点元信息，但不含"取值优先级"语义。
- 导入预检的错误码族 `importer_mapping_stale:*` 校验的是"代码写死映射是否仍被已发布定义支持"（关系码、词表项），不校验来源与取值优先级。

### 2.2 问题

1. **优先级不可复核**：同一字段被多个来源给出不同值时，谁覆盖谁只存在于执行者的记忆与说明里，评审者无法从数据反推。
2. **provenance 粒度到实体不到字段**：`sources` 是实体级证据列表，回答不了"这个字段的值来自哪个来源"。
3. **被覆盖值不留痕**：按优先级取值后只剩最终值，后续改判（新来源出现、原来源被证伪）没有依据。
4. **同优先级冲突无固定路径**：两个同档来源给出不同值时，处理方式随人而异。

### 2.3 建议做法

| 方向 | 做法 |
| --- | --- |
| 优先级声明化 | 在 definitions（或来源库注册）声明来源档位 `official > database > community`，导入按声明解析取值，不按执行者习惯 |
| 字段级 provenance | 导入时为每个被赋值的字段记录来源标识（来源 code + 来源地址），随实体落库，读接口按字段返回 provenance |
| 冲突按优先级取值 | 同字段多源冲突按声明优先级取值；低优先级值不丢弃，作为"被覆盖值"保留在属性或修订快照中 |
| 同档冲突 | 不自动取值，标记为待人工裁决项并在预检结果里列出 |
| 与现有落点并存 | `sources` / `edit_note` 继续作为实体级证据保留；字段级 provenance 是更细一层，不替代实体级证据 |

### 2.4 待办

| 待办 | 可验证的完成判据 |
| --- | --- |
| 来源优先级声明 | 优先级可从已发布 definitions（或来源库注册）读取；单测断言：同字段两源冲突时，取到的是声明档位更高的一方，且顺序改声明后取值随之改变 |
| 字段级 provenance 落库 | 导入后读回实体，能按字段得到来源标识；无来源的字段在 provenance 中显式缺省而非默认填充；契约文档与 DTO 同步声明该字段 |
| 被覆盖值保留 | 冲突场景单测断言：最终值来自高优先级来源，同时低优先级值可在属性或修订快照中读回 |
| 同档冲突转人工 | 预检或导入结果返回待裁决条目清单；列表为空时才允许静默完成导入 |

> 说明：当前"来源声明"是实体级证据，字段级 provenance 尚无结构化承载——本节建议是从零建立这层结构，不是在既有字段上改名。

## 3. 数据完整性自检

### 3.1 现状

- 检查主体是只读脚本 `scripts/check_data.py`：发布态与翻译、结构归属（以 `definitions.structure` 为准）、关系（重复边/端点不可见/未知码）、定义名称占位、覆盖度硬闸门（乐队必须有 `member_of` 入边、发行版必须有载体）与提示项（影像作品无篇目、载体无曲目、作品无关系、图片缺口）。退出码 0/1 可直接当发布闸门。
- 写入侧另有导入预检 `importerPreflight`（`backend/internal/catalog/importer.go`）：写库前只读校验整份载荷（章节树拓扑、显式表达引用、字段码归属、写死映射是否过期），失败即零写入。
- `definitions.structure` 已能声明各层级的结构归属：结构字段、允许作为目标的层级、是否必填、候选按哪个字段过滤（`StructureRule` / `StructureField`，`backend/internal/catalog/types.go`），校验与编辑器共用这份声明。
- 关系码失效在读路径上是宽容的：`relations` 读取时校验失败静默跳过，表现为"读不到"而不是报错。

### 3.2 问题

1. **没有固定周期与留档**：脚本要人工执行，报告不落档，跨时间无法比对趋势。
2. **覆盖面不成清单**：缺父级、缺翻译、缺图片、关系码缺失、同域父节点异常、来源缺失等没有统一入口。
3. **层级知识会被重复实现**：不消费 `structure` 声明的检查脚本必须自己写一套"哪个层级该挂哪个层级"的规则，与写入校验各说各话。
4. **失效边只在读路径静默**：非法关系边只表现为"读不到"，没有汇总出口。

### 3.3 建议做法

把检查项固化为报告的固定字段（检查项、严重级、命中数量、样例标识列表），并接定时任务留档；检查项以 definitions 为基准，能复用 `structure` 的不另写层级知识：

| 检查项 | 口径（基准） | 严重级 |
| --- | --- | --- |
| 缺父级 | `structure.<kind>` 中 `required` 为真的结构字段为空 | 阻断 |
| 同域父节点异常 | 父节点 kind 不在 `StructureField.TargetKinds` 内（`target_kinds` 为空表示同层，即同域） | 阻断 |
| 层级不满足 | 实体的实际结构不满足 `structure.<kind>` 声明（如表达未挂作品、载体未挂发行） | 阻断 |
| 关系码缺失 | 关系的 `type` 不在已发布 definitions 中，或该码已停用 | 阻断 |
| 缺翻译 | 必备语种缺题名或摘要 | 警告 |
| 缺图片 | 无封面且无官方图标记 | 提示 |
| 来源缺失 | 实体无 `sources` 且其修订无来源记录 | 警告 |

- 检查只读、不改数据；失败不阻塞写入口，由运维按报告决定处置。
- 报告本身可进 CI 产物或部署留档，便于跨时间比对。
- 第 2 节的字段级 provenance 落地后，"来源缺失"细化到按字段判定。

### 3.4 待办

| 待办 | 可验证的完成判据 |
| --- | --- |
| 定时任务与留档 | 检查以固定周期执行并落档报告；两次报告可比对（按检查项给出数量变化） |
| 复用 `structure` 判定 | 单测断言：修改 `structure` 声明（如把某结构字段改为必填）后，检查结果随之变化，且不需要改检查代码 |
| 关系失效边显式化 | 读路径静默跳过的非法边在检查报告中列出（含边标识与原因），不再只体现为"读不到" |
| 严重级与闸门口径固化 | 各项检查的严重级在报告与 CI 判定中一致；构造缺父级、同域父节点异常、关系码缺失三类夹具时，报告分别命中且严重级正确 |

## 4. 前端外壳组件化

### 4.1 现状

- 外壳组件已存在：`frontend/src/components/ui/{PageShell,Card,SectionTitle,TabPanel}.tsx`。`PageContainer` 是"最大宽度 + 水平内边距"的唯一出处（`max-w-page` / `max-w-narrow`，`narrow` 包在 page 档容器内保证左基线一致）；`TabPanel` 由组件内部把 `activeKey` 当 React key 挂载，调用方漏不掉重挂载；导航条与管理台内栏复用同一容器。
- 自检已接：`node scripts/check_page_shell.mjs`（已接 CI frontend job）拦页面级自写容器规则；命中只允许出现在外壳组件内。
- 页签动画统一在 `.mf-tabpanel`（`frontend/src/app/globals.css`），只挂在面板/列表容器上，且必须让容器 key 随切换源变化才会重放。
- 头部高度令牌 `--mf-header-h` 统一顶部偏移（各页粘性定位用它计算），主题令牌（surface / line / text 系）与密度口径（区块内边距、区块间距、标题分隔线）已统一。
- 探索页筛选是标签驱动的：标签云来自真实的聚合标签，骨架保留固定 kind 的分层分组，类型不再作为筛选入口。
- 仍存在的残留：页面**内部区块**仍手写卡片类（如详情页各 section 的 `p-4 sm:p-5`），自检目前只拦页面级容器；部分组件仍按 kind/type 分支渲染或维护固定映射。

### 4.2 问题

1. **内部区块口径仍逐页手写**：自检覆盖不到内容级卡片，密度调整要逐页改、逐页验。
2. **写死的类型知识仍有残留**：结构归属区、资源分节、导航入口已按 definitions 渲染；展示名与字段语义判定也已收敛（kind 名走 `definitions.kinds`，前端字典只作兜底；时长字段按字段码认定，不再嗅探单位文案）。**剩余的是按 kind 码分支的展示逻辑与兜底清单**：图谱组件的配色/图标分支、`EntityEditor` 里「哪些层级有定位字段」的固定数组、以及前端在服务端未给时的骨架兜底清单——新增类型或层级时这部分仍可能要改前端。

### 4.3 建议做法

| 组件 | 职责 | 页面不再自写 |
| --- | --- | --- |
| PageShell | 最大宽度、水平内边距、纵向间距、主区包装 | `max-w-*`、`px-*`、`py-*` |
| TabPanel | 页签容器：挂动画类并按切换源重挂载 | 动画类名与容器 key 逻辑 |
| Card | 卡片圆角、边框、背景与内边距 | 卡片 `p-*` 与边框/背景组合 |
| SectionTitle | 区块标题排版与分隔线密度 | 标题字号与分隔线内边距 |

- 规则：宽度、内边距、动画只在外壳组件内定义，页面禁止自写这三类工具类；用一条可自动执行的检查兜住，而不是靠约定。
- 写死的类型知识（层级、类型、字段、词表）改为查 `definitions`（`structure` / `types` / `templates` / `vocabularies`）；声明缺失时报缺口，不在代码里补默认分支。
- kind 展示名一律走 `definitions.kinds`（`getKindName()`），前端字典只作兜底；字段语义用定义里的声明判定，不靠显示文案。

### 4.4 待办
