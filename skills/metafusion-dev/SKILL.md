# MetaFusion 项目开发技能

本技能是**本仓库**的工作约定，适用于所有改代码、改文档、改部署的任务。
与 `AGENTS.md` 冲突时以更具体的一方为准；与用户当次指令冲突时以用户指令为准。

技能放在仓库根的 `skills/` 下（与 `metafusion-skills` 仓库同一布局），**不要放进任何单一厂商的私有目录**
（`.cursor/`、`.claude/` 之类）：那些目录是某个编辑器的工作区状态，换一个 agent 就看不见了。

## 1. 先维护本地敏感开发日志（`docs-local/`）

`docs-local/` 被 `.gitignore` 排除，**永不提交**，专门存放"只在本机有意义、但下一次接手的人必须知道"的信息：

| 文件 | 必须包含 |
| --- | --- |
| `docs-local/README.md` | 目录用途与规则 |
| `docs-local/dev-log.md` | 阶段判断、关键决定、已踩过的坑（倒序） |
| `docs-local/deploy/server-connection.md` | 开发服务器、部署目录、操作注意事项 |
| `docs-local/deploy/paths.md` | 主工程与各子项目路径、一键部署入口 |

**每次任务开始时**：读一遍 `docs-local/`（若不存在则创建，模板见第 5 节）。
**每次任务结束前**：如果这次改动涉及部署方式、路径、服务器约定、阶段变化或发现新坑，
**必须**把对应信息写回上述文件。判断标准：这条信息"对下一次接手的人有用"就写，"只是操作流水"就不写。

凭据规则：**口令、私钥、PAT 一律不复制**进本仓库任何文件（含 `docs-local`），
只记录"到哪里取"（例如本机的机器信息文件），并写明来源路径。

## 2. 提交纪律（本仓库覆盖"未要求则不提交"的默认行为）

- 完成一个逻辑单元就 `git commit`，不要攒到最后、也不要等用户再提醒。
  一个单元可以包含相互依赖的多个文件；机械重命名/格式化单独提交，不与逻辑变更混在一起。
- Conventional Commits（`feat/fix/chore/docs/style/refactor/test/build`），首行 < 72 字符，风格与近期 `git log` 一致。
- 提交前先 `git status`，只 `git add` 本次任务相关文件；排除 `.env`、密钥、token；
  `git diff --cached --check` 与 `git diff --cached` 确认无敏感信息、无无关改动。
- 改到哪验到哪：`backend/` → `go build/vet/test`；`frontend/` → `tsc --noEmit` 与构建；
  compose/nginx → CI 的 `compose-lint`（本地不跑 docker）。
- **不要 push**，除非用户明确要求；禁止 force push `main`/`master`；不要改 git config、不要 `--no-verify`；
  不要 `--amend`，除非用户明确要求且该提交由你创建、未 push。

## 3. 开发规范

1. **注释精简高效**：只写"为什么这样做/约束是什么"，不复述代码在做什么。
   踩过的坑要写成一行原因（例如"合并响应没有长度，客户端返回 0"），这类注释是资产。
2. **单文件不过长**：接近 500 行就该拆分（按职责拆文件，不按类型堆砌）。
   现有大文件是历史包袱，改动时优先顺手拆分而不是继续加长。
3. **子代理并行处理模块**：多个互不依赖的模块/仓库改动，用并行子代理推进；
   子代理任务要自包含（它们看不到当前对话），并明确"不要碰别人的未提交改动"。
   需要共享上下文的拆分用 fork 型子代理。
4. **改代码后同步文档**：接口、行为、部署方式一变，同一批次里更新 `docs-site/`、各服务 README、
   OpenAPI 描述。文档以**代码实际行为**为准，发现历史描述与实现不符时改文档并在提交信息里说明。

## 4. 多语言与国际化铁律

- **UI 文案零硬编码**：所有用户可见文本（标题、按钮、表单标签、占位符、提示、空状态、错误）都必须走
  `useI18n()` 的 `t("key.path")`，在中英字典（及 zh-TW / ja-JP）中同步增补；禁止 `t(key) || "中文兜底"`。
- **动态术语从数据取**：实体类型、关系类型、词表项、模板分区等名称一律来自服务端 definitions 的多语言字段，
  用现成 helper（如 `getFieldName` / `getTermName` / `local`）解析，不写死显示文案。
- **数据侧多语言**：实体题名/简介/别名存在统一 DTO 的 `translations`（按 locale 分组的对象）里；
  原语言题名归属对应翻译行，不把其它语种题名塞进实体级 `aliases`。
- 展示回退链：请求语言 → `en-US` → `original_language` → 基础字段；读取与写入字段分离，展示值不回写。
- 历史遗留的表名（`work_translations` / `artist_translations` / `franchise_translations` / `ontology_terms`）
  与 `CanonicalEntry`/`Artist`/`Franchise` 等旧实体名**已退役**，不要再按它们写代码或文档。

## 5. 项目理念与需求边界

**定位**：开放的多媒体元数据共建库 + 受控资源分发站（类似 MusicBrainz / Bangumi，但不是通用知识库）。

- **开放元数据**：高度结构化（作品 / 内容单元 / 表达 / 发行 / 载体分层）、每条实体有稳定 UUID 与修订历史、
  提供标准 REST API 供第三方与 AI Agent 调用。
- **社区共建与考据**：编辑留痕、可追溯、鼓励 `edit_note` 与来源；重复词条走合并而不是覆盖。
- **受控分发**：内容寻址去重、冷热分层存储、直传与预签名下载、访问控制与审计。
- **工程原则**：
  - 固定实体骨架 + 动态定义（类型/关系/字段由 definitions 驱动），**不把能力写死在代码里**；
  - 单一职责：元数据 / 账号 / 互动 / 存储各自独立，跨系统只通过 HTTP 契约与事件交互，
    **禁止跨库 JOIN、禁止复制对方的表**；
  - 一切结论要有证据：能跑测试就写测试，跑不了就说"未验证"，不拿"编译通过"当验证。

## 6. 初始化 `docs-local/` 的最小模板

若目录不存在，按以下内容创建（`.gitignore` 已排除该目录，无需再改）：

```
docs-local/
  README.md                      # 用途、规则、目录结构
  dev-log.md                     # 阶段 + 关键决定 + 已知坑（倒序）
  deploy/server-connection.md    # 站点、主机名、部署目录、操作注意事项、凭据来源（不含凭据本身）
  deploy/paths.md                # 主工程与各子项目路径、一键部署入口
```
